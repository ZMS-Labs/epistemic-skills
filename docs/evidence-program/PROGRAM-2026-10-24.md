# Evidence program — design and preregistration

**Date:** 2026-10-24. **Status:** DESIGN. This program is **not adopted on
its own say-so.** No Wave 2 epoch in §4 runs until an independent
methodological review (§6) has examined this design and the Wave 1
batteries against evaluation best practice and its verdict is recorded.
The review is a gate, not a formality; nothing in this document softens a
finding to pass it. **Review status (2026-10-24):** the review is complete
and recorded in `METHODOLOGICAL-REVIEW-2026-10-24.md`; its required fixes
F1–F8 are landed (see the amendment record), and the gate terms stated
there govern which epochs may now run.

**Why this exists.** The 2026-10-24 assessment of v7.3.0 found efficacy
evidence NONE for eight skills — `epistemic`, `metacognate`,
`perspective`, `health`, `triage`, `watch`, `manifest`, `did-it-land` —
exactly the eight whose `SKILL.md` carries *"Activation discipline:
design-argued; no shipped trigger battery as of this change."* It also
found: no control arm for gauntlet's arbitrator certification;
evidence-locked-uat's battery scoring canned responses only; second
epochs promised for `context-audit`, `open-questions`, and `outsource`
and never run; and triage's Oracle corpus specified in its `SKILL.md`
but not shipped. This program designs and builds the missing
instruments (Wave 1) and preregisters the runs that use them (Wave 2).

**Known deviations, stated rather than hidden:**

1. **N=1 per fixture in the trigger epochs** (repo convention). These
   are smoke-scale conformance probes, not rate estimates; no epoch
   result may be quoted as a percentage of anything except its own
   fixtures. The paired trials (E15) use replicates (N=3 per arm per
   scenario) because their claim is comparative.
2. **Holdout subsets are small** (3 of 13). They detect gross tuning,
   not subtle overfitting. They are a floor, not a guarantee. Stated
   plainly (review fix F8): the holdout flags sit in the public
   `fixtures.json`, and they burn on the first skill edit — once a
   skill's text changes, anyone editing it has seen the marked fixtures,
   so they stop being a holdout. They protect only against epoch-runner
   tuning (dispatch text, prompts, example selection by the runner of
   record); they are not a blind against anyone who has read the
   fixtures.
3. **Scorers score declared responses**, extracted per dispatch
   contract §3 — not behaviour in a live harness. A pass shows an agent
   *reports* the disciplined decision under the pinned contract.
4. **Simulation clause.** All Wave 2 epochs are simulations: no real
   systems are probed, deployed, watched, or custodied. Verdicts on
   planted evidence states (triage oracle, did-it-land fixtures) test
   judgement against described evidence, not perception of real
   evidence.
5. **Metacognate and perspective contracts are battery-defined** (§5).
   The batteries score against an observable output contract the skills'
 own text does not yet contain. A pass therefore supports conformance
   to the battery's contract, which is one step further removed from
   "the skill as written works" than for the other six. This is stated
   in both READMEs and is the review's business to weigh.

## 2. Wave 1 — built instruments (2026-10-24)

### 2.1 Trigger-and-scope batteries for the eight untested skills

Each battery: 13 original fixtures (positive fires, hard negatives,
boundary cases against neighbouring skills), every fixture carrying a
`clause` field quoting the `SKILL.md` trigger/do-not-fire text it tests
and 3 marked `holdout`; a stdlib-only deterministic scorer in the
existing batteries' pattern (fail-closed on malformed responses);
synthetic `balanced` / `overfiring` / `underfiring` / `parody` example
sets the scorer must pass/fail respectively, proven by
`tests/run_tests.py`; a README with the pinned live-epoch response
contract; and `results/BLOCKED.md` recording that no epoch has run.

| Skill | Battery | Decision the contract scores |
|---|---|---|
| epistemic | `skills/epistemic/evals/trigger-and-scope/` | use-method vs no-fire; method named from the suite vocabulary; claimed use requires instructions actually loaded; unavailable instructions → limit stated, no claimed use |
| metacognate | `skills/metacognate/evals/trigger-and-scope/` | examine vs no-fire; battery-defined output contract (see §5) |
| perspective | `skills/perspective/evals/trigger-and-scope/` | apply-lens vs no-fire; battery-defined output contract (see §5); adjudication fields are a scoring failure — lens count is not adjudication |
| health | `skills/health/evals/trigger-and-scope/` | readout vs no-fire; per-subject states and roll-up checked against the aggregation rule (any `UNKNOWN` forbids an `OK` roll-up; ordering CRITICAL → UNKNOWN → WARN → OK) |
| triage | `skills/triage/evals/trigger-and-scope/` | investigate vs no-fire; verdict shape (CAUSE requires a discriminating observation; UNKNOWN names no cause) |
| watch | `skills/watch/evals/trigger-and-scope/` | commission vs no-fire; commission state in the 5-state vocabulary; BLOCKED requires a closed-vocabulary reason plus dated block evidence; PROVEN requires a production-path proof object with a re-proof boundary; the session/skill itself is a rejected substrate |
| manifest | `skills/manifest/evals/trigger-and-scope/` | open / resume / verify vs no-fire; open requires a verbatim instruction and a complete four-field envelope; an unavailable acceptance path blocks opening; self-acceptance never scores as accepted |
| did-it-land | `skills/did-it-land/evals/trigger-and-scope/` | verify-landing vs no-fire; LANDED requires an observation at the consumer of the artifact the runtime loads; source-only evidence forces UNVERIFIED; observed-then-reverted forces REVERTED |

### 2.2 Triage behaviour-oracle corpus

`skills/triage/evals/behaviour-oracle/` — the corpus triage's Oracle
section specifies: one planted case per trigger clause (4) and per
degraded-operation row (5), the plausible-cause core case, and two
positive controls (an earned `CAUSE`; an earned `NOT-BROKEN`). It builds
around the shipped sentinels
(`contracts/epistemic-events/sentinels/triage-plausible-not-observed.json`,
`triage-lying-readout.json`, and the `operational-scenarios.json`
controls) as concrete scenario instances rather than duplicating their
abstract response records. The scorer asserts the verdict the planted
evidence supports **and** that the most plausible candidate is not named
as the cause without a discriminating observation. 12 fixtures, 3
holdout.

### 2.3 What Wave 1 deliberately did not do

No `SKILL.md` was edited. No epoch was run. No fixture was copied from an
existing battery. The eight skills' *"no shipped trigger battery"* lines
remain true until a battery survives review and an epoch runs — the
batteries existing is not the testing being done.

## 3. Per-battery claim statements

A pass in a Wave 2 epoch supports exactly the claim in the middle column
— no more. (Each battery README carries the same statement; if they ever
disagree, the README is wrong and gets corrected, because the epoch
dispatches quote the README.)

| Battery | A pass supports | A pass does NOT support |
|---|---|---|
| 8 trigger batteries (general) | An isolated agent given the skill reports the fire/no-fire decision and mode the skill's own trigger text prescribes, on these fixtures, under the pinned contract | That the method improves any outcome; that firing behaviour matches in a live harness; a population rate |
| health | The above, plus: planted degradations are reported as `UNKNOWN`, never absorbed into an `OK` roll-up | That real probes are wired, or that a real system's state was read |
| triage (trigger) | Fire/no-fire conformance plus verdict-shape discipline on declared responses | Diagnostic accuracy |
| triage (oracle) | On planted evidence states, the returned verdict is the one the evidence supports; plausibility is not converted into cause | Field diagnostic accuracy; repair correctness |
| watch | Commission-state honesty on described facts (blocked stays blocked, proven requires proof) | That any observer exists or watches anything |
| manifest | Custody-mode selection and envelope/acceptance discipline on declared responses | That the custody core executed, or that a mission survived a real interruption |
| did-it-land | Landing verdicts track the evidence state (source-only → UNVERIFIED; observed → LANDED; reverted → REVERTED) | That any real change was observed at a real consumer |
| metacognate / perspective | Conformance to the battery-defined observable contract (see §1 deviation 5) — and results must always be reported in exactly those terms, never as evidence about the skills as written (**binding constraint**, methodological review 2026-10-24: if that qualifier is ever dropped, those two skills' evidence grade reverts to NONE) | That the skills as written produce these outputs unprompted, or that reflection/lenses improve decisions |
| gauntlet control arm (E14) | A comparative claim only: certified-seat catch rate vs plain-arbitrator catch rate on the same planted flaws | Certification validity in general; anything about other seats |
| UAT live epoch (E13) | Live agents route the 4 triage fixtures as the shipped scorer prescribes | That UAT itself executes correctly end-to-end |
| Paired hard trials (E15) | A comparative claim under adversarial scenario conditions: skill arm vs no-skill arm on rubric scores fixed in advance | Field outcome improvement; behaviour under real operational pressure |

## 4. Wave 2 — preregistered epochs (run only after the §6 gate clears)

**Mechanics common to E1–E13** (fixed now): one fresh isolated
general-purpose subject per fixture; model family claude-fable-5 unless
the epoch says otherwise (same-family caveat recorded); dispatch follows
`LIVE-EPOCH-DISPATCH-CONTRACT.md` verbatim — pinned contract quoted from
the battery README with prior-epoch history stripped, opaque keys
`sha256(fixture-id)` first 12 hex, dispatch ordered by key, subjects read
only the skill core and core-directed references; the battery's shipped
`score.py` runs unmodified; artifacts land in
`<battery>/results/<date>/` as `responses.json`, `scorer-report.json`,
`dispatch-map.json`, `RESULTS.md`; holdout fixtures are scored with the
rest and also reported as a separate line in `RESULTS.md`; an epoch
**passes** only on scorer exit 0, any fixture failure is an epoch FAIL
recorded and characterised as (a) conduct, (b) reporting shape over
correct conduct, or (c) mode/instrument selection; verdicts land on the
epoch register per dispatch contract §7. Non-binding calibration
expectation, stated now: ≥ 90% fixtures passing per trigger battery,
with verdict-shape (class b) failures the plausible regression vector
for the verdict-bearing skills (health, triage, did-it-land, watch,
manifest). This expectation is not a gate.

**No silent re-runs (review fix F3).** No epoch may be repeated under
the same ID, and no failed epoch may be quietly re-run until it passes.
Any repeat of an epoch is a new preregistered epoch with a new ID; the
prior epoch's FAIL stands in the record, unedited; and the repeat's
reason is recorded in advance — in this document's amendment record,
before the repeat is dispatched.

## 5. The scorability gap (metacognate, perspective)

Neither skill's text contains a verdict vocabulary, required output
fields, or any falsifiable output shape — which is why they were
untestable. The Wave 1 batteries resolve this **from the battery side**:
each defines a minimal observable contract (metacognate: outcome named
distinct from its proxy, decisive assumption, discriminating observation,
and a four-value verdict — approach-retained / approach-corrected /
question-reframed / confidence-recalibrated; perspective: lens named,
bounded question, finding in a five-value vocabulary, adjudication
expressly forbidden) and scores against it.

**Proposed item P1 (separate, NOT in this wave, NOT assumed approved):**
adopt the battery contracts into the two `SKILL.md` files as their
output sections. Until P1 is decided and, if approved, executed, every
metacognate/perspective result must be reported as conformance to a
battery-defined contract — never as "the skill works". The §6 review
should rule on whether battery-side contracts are acceptable evidence
instruments at all, or whether P1 must land first. **Review ruling
(2026-10-24):** the battery-side contracts are acceptable instruments,
under a binding constraint — results are always reported as conformance
to the battery-defined contract, never as evidence about the skills as
written; if that qualifier is ever dropped, those two skills' evidence
grade reverts to NONE.

## 6. The gate: independent methodological review

Before E1 is dispatched, a reviewer who did not author this program or
the batteries reviews, at minimum:

1. **Preregistration discipline** — is everything in §4 actually fixed
   (N, arms, scoring, interpretation), or are there residual degrees of
   freedom an epoch runner could exploit?
2. **Blinding** — opaque keys, subject isolation, README-contract
   stripping, and E15's arm-label blinding at scoring time.
3. **Control arms** — E14's plain-arbitrator instruction (is it a fair
   control, or a strawman?), E15's no-skill arm parity.
4. **Scorer validation** — the balanced/over/under/parody sets: do the
   parodies represent real failure patterns, and does `run_tests.py`
   actually prove discrimination?
5. **Sample-size honesty** — §1 deviations 1–2; whether any epoch's
   planned reporting could overclaim a rate.
6. **Construct validity** — §3's claim table, battery by battery: does a
   pass really support the stated claim and only that claim?
7. **Holdout separation** — 3/13 holdout marking, the no-tuning rule,
   separate holdout reporting.
8. **Cross-model replication** — E16's trigger conditions and the
   same-family caveat's prominence.

The reviewer may block any epoch, demand battery changes, or reject the
battery-side contracts in §5. Findings are answered in the open, in this
document's amendment record — not softened, not routed around. Wave 2
begins only with the review's recorded verdict.

## 7. What "done" means

- **Wave 1 done:** this document committed for review; 8 trigger
  batteries + the triage oracle corpus shipped with green
  `tests/run_tests.py` in all 9 new batteries; a Wave 1 report stating
  per-skill fixture counts, clause coverage, and test results. (Batteries
  shipped ≠ testing done; §2.3.)
- **An epoch done:** its four artifacts committed, scorer exit code
  recorded, failures characterised, holdout line reported, verdict on
  the register — pass or fail.
- **The program done (Wave 2):** E1–E15 run and recorded (E16 run or
  recorded PENDING with reason), including the nulls. At that point —
  and only then — the eight skills' evidence grade changes from NONE to
  whatever the epochs support, and the README's evidence accounting can
  be updated to match reality.
- **E16's PENDING verdict:** if no second-family lane is available, the
  PENDING verdict (with its reason) is recorded by the coordinator
  closing the program, in the program-close record, at program close —
  not by an epoch runner and not left unrecorded.
- **Never "done" by this program:** outcome efficacy. Nothing in Wave 1
  or 2 shows the skills improve real-world results; that requires field
  telemetry (real `runs/` ledgers, which today contain only synthetic
  exemplars) and is a Wave 3 question this program names but does not
  design.
