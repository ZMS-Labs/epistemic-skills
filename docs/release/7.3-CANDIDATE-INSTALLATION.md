# 7.3.0 — local review and publication checkpoints

This is the **pre-publication review checklist** for 7.3.0. Manifest version
7.3.0 identifies package content; it does not prove a tag, public asset,
installation or loaded-host behavior. Actual publication is recorded by the
tag, Release and receipts, not by this preparation checklist. Published 7.2 snapshots and receipts
remain historical support references. Current installation and handbook source
now target the proposed 7.3 release, whose tag must be checked independently.

## Review the candidate locally

Use the actual local candidate checkout supplied by the task owner. Confirm
its branch, base, staged diff and tree identity before any authorized host load:

```sh
git branch --show-current
git rev-parse HEAD
git status --short
git diff --cached --check
git write-tree
python3 .github/scripts/build_openai_bundles.py --check
```

The proposed source branch is `codex/consensus-threads-7.3`; until pushed under
separate authority it is local only. A host that accepts a local plugin source
can load that exact directory only when installation is separately authorized.
Do not install another copy beside an existing copy. A host load must then
verify the loaded source, seventeen-skill inventory and version; none was
performed in this source-only task.

The candidate Kimi marketplace targets the prospective `v7.3.0` release.
That pin expresses the intended immutable source; it is not evidence the tag
exists. Use local source until authorized publication and tag reachability are
verified. Previously published 7.2 snapshots remain available at their existing
immutable coordinates.

There are two timing constraints, not permission to invent evidence:

1. Release preparation can write **prospective** versioned URLs and offline
   verify every target path in the frozen source. Remote tag/asset reachability
   can only be verified after the tag/Release exists. Mark those checks pending
   until then; never report a planned URL as a verified publication.
2. The handbook publisher requires an already published release and a public
   committed docs ref. It cannot truthfully publish a local uncommitted 7.3
   candidate. The offline `--check` uses current source paths and the current commit inventory;
   live staging retains the actual tag/Release/public-docs-ref guards. Satisfy
   those guards after publication. Preserve immutable 7.2
   snapshots and receipts.

RELEASING.md still requires final alignment before publication. This separation
does not waive that gate or turn the current candidate into a conforming release.
It prevents local source preparation from depending on a fabricated future tag.
